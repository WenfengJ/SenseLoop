# 评委可能会问的问题

这份文档用于准备预选提交、路演答辩和现场 Demo。  
回答原则：先讲用户价值，再讲技术实现；主动说明边界，不夸大医疗能力。

## 1. 你用了 Anker 哪个硬件？

当前主硬件是 **soundcore Work 录音豆 / 录音笔**。

推荐回答：

> 我们把 soundcore Work 从会议录音场景延展到夜间健康声音采集。它可以记录打鼾、咳嗽、夜醒、起夜、环境噪声和用户重点标记。SenseLoop 的价值不是只回放录音，而是把这些声音变成第二天的饮食、运动和恢复建议。

## 2. 为什么是中医四诊 Agent？

推荐回答：

> 因为健康管理不是单一指标能解释清楚的。打鼾只是“闻诊”线索，舌苔是“望诊”线索，排便和症状描述属于“问诊”线索，未来心率、步数、穿戴体征可以作为“切诊”线索。我们用“望闻问切”组织多模态输入，再交给一个有记忆的 Agent 追问、解释和沉淀报告。

补充点：

- 四诊是产品信息架构，不是宣称自动诊断。
- 它让页面不再是零散功能，而是围绕健康线索组织。
- 对评委来说，这也是区别于普通睡眠 App 的清晰叙事。

## 3. 和普通健康 App 有什么区别？

推荐回答：

> 普通健康 App 往往告诉用户昨晚睡了多久、打鼾多少、得了几分。SenseLoop 更关注“今天怎么办”。它把 soundcore 夜间声音、舌苔、排便、体检资料和问诊对话放进同一个健康档案，生成今天可执行的建议，并在后续问诊和报告里持续积累。

一句话：

> 不是只记录数据，而是把数据变成个人健康 Agent 的长期上下文。

## 4. RAG 知识库从哪里来？

推荐回答：

> 第一版知识库不是从网上随便抓，而是开发者手动整理和审核。内容包括四诊解释、睡眠声音边界、舌诊标签、排便/饮食/口气管理规则、药食同源边界、风险提醒和隐私/医疗边界。后续会做知识库后台，支持文档导入、切片、审核、版本管理和引用展示。

当前状态：

- 已有占位中医知识卡和检索接口。
- PostgreSQL + pgvector 已准备好。
- 第一批资料由开发者筛选、切片、导入。
- GraphRAG 是后续路线，不是第一轮必须能力。

## 5. AI 误判怎么办？

推荐回答：

> 我们把 AI 放在“解释和追问”的位置，不让它直接做医疗结论。关键风险由规则和边界控制：连续异常、明显不适、发热、出血、严重睡眠异常时，提示继续观察或咨询医生。用户也可以修正标签，例如鼾声、饮食、排便和舌苔信息，修正会进入后续档案。

设计原则：

- AI 回答使用“倾向、可能相关、建议观察”。
- 不说“确诊”。
- 高风险情况提示就医。
- 用户修正优先于模型猜测。
- 报告展示依据来源。

## 6. 是否诊断疾病？

推荐回答：

> 不诊断疾病。SenseLoop 是日常健康管理和趋势观察工具，不替代医生，也不判断具体疾病。比如我们可以说“昨晚鼾声片段增多，今天建议降低运动强度并继续观察”；不能说“你患有睡眠呼吸暂停”。

能说：

- “建议观察。”
- “可能与睡眠恢复、饮食或口干有关。”
- “如果持续出现，请咨询医生。”

不能说：

- “你得了某种病。”
- “这个建议可以替代医生。”
- “中医辨证等于医学诊断。”

## 7. 隐私怎么做？

推荐回答：

> 我们把数据分级处理。普通档案、健康记录、舌图、体检报告、音频文件敏感程度不同。长期记忆默认保存摘要，不默认把原始图片、PDF、音频长期暴露给模型。Agent 工具调用必须带 `profileId`，不能跨用户读数据。用户可以删除记录和文件。

具体设计：

- 原始文件与摘要分离。
- 图片/PDF/音频属于敏感或高敏数据。
- 数据库保存文件索引和摘要。
- 当前 MVP 文件暂存在服务器本地云磁盘。
- 生产迁移对象存储和短期签名 URL。
- 家庭共享只展示摘要，不展示原始敏感内容。

## 8. 为什么本地磁盘不先上对象存储？

推荐回答：

> MVP 阶段先用服务器本地云磁盘，是为了快速验证上传、摘要、档案绑定和 Agent 引用链路。它不是最终生产方案。生产环境会迁移到对象存储，比如 OSS、S3、R2 或 MinIO，数据库只保存文件索引、哈希、摘要和权限信息。

补充：

- 比赛阶段数据量小、链路验证优先。
- 本地磁盘部署简单，故障点少。
- Roadmap 已明确对象存储迁移。
- 迁移不会推翻业务表结构。

## 9. soundcore 没接真 SDK 怎么解释？

推荐回答：

> 工程上我们把 soundcore 放在 adapter 层。当前没有真实 SDK 时，用 mock 或真实样例录音生成同样的 `SleepAudioEvent` 数据结构；拿到 SDK 后替换 adapter，不需要重写前端、报告、问诊助手和数据库。现场如果 SDK 未开放，我们会用真实音频样例和手动标注展示完整链路。

强调：

- 当前不是忽略硬件，而是先固定数据协议。
- SDK 接入是 adapter 替换问题。
- Demo 已明确展示数据来源：mock / upload / soundcore_sdk / audio_model。

## 11. 为什么 Anker 做这个有价值？

推荐回答：

> Anker 已经有音频、智能硬件和家庭设备能力。SenseLoop 的机会是把录音笔从“记录工具”升级为“健康入口”。soundcore Work 可以先验证夜间声音场景，未来可以延展到耳机、手环、手表、床头设备或家庭健康设备，形成软硬件协同的健康助手。

## 12. 为什么睡眠声音是 MVP 主线？

推荐回答：

> 因为夜间声音高频、真实、和 soundcore 硬件强相关。打鼾、咳嗽、夜醒、起夜和环境噪声，用户平时很少系统观察，但这些变化会直接影响第二天状态。用它作为 MVP 主线，既贴合 Anker 硬件，也能快速形成差异化。

## 13. 舌苔和大便为什么要加入？

推荐回答：

> 它们不是为了把产品做散，而是补充 soundcore 听不到的信息。睡眠声音告诉我们“夜里发生了什么”，舌苔、排便、饮食和体检资料帮助解释“身体状态可能在哪里变化”。这些信息进入同一个档案后，Agent 才能更像一个连续追问的健康助手。

边界：

- 需要用户主动记录或上传。
- 默认不自动拍摄隐私内容。
- 只做健康管理参考。

## 14. 如果评委问“你们的算法亮点是什么？”

推荐回答：

> 算法亮点不是单一模型，而是四诊 Agent 工作流。我们把输入分成望、闻、问、切四类，先抽取结构化健康线索，再结合 7 天记忆、知识库检索和风险规则，由 Agent 生成建议和追问。后续可以用 LangGraph 风格的 State、Node、Tool 和 Memory，把睡眠解释、舌诊分析、报告解读、知识检索和风险判断串起来。

技术关键词：

- 四诊输入层。
- 结构化特征抽取。
- 近 7 天记忆。
- RAG 引用。
- 风险规则。
- Agent 工具调用。
- `profileId` 数据隔离。

## 15. 24 小时现场还做什么？

推荐回答：

> 我们不是从零开始做，而是在已部署版本上打磨。现场优先接真实 soundcore 样例，补录屏和截图，打磨问诊问题，准备评委问题回答，并验证线上部署稳定性。技术上会优先增强真实声音数据、资料解读、问诊助手和演示闭环。

优先级：

1. 接真实 soundcore 样例或上传音频。
2. 固定 3 个问诊问题。
3. 补核心截图。
4. 录制 3 分钟演示。
5. 验证线上部署。
6. 准备 Q&A。

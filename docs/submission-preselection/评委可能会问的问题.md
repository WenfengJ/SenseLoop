# 评委可能会问的问题

这份文档用于准备预选提交、路演答辩和现场 Demo 时的高频问题。  
能确定的问题已直接补充答案；需要你根据官方现场资源、队伍情况或提交表单确认的问题，用 `？？待补充` 标记。

## 1. 你用了 Anker 哪个硬件？

当前主硬件使用 **soundcore Work 录音豆**，用来验证夜间声音健康洞察。  
可选使用 **eufy 摄像头** 验证非隐私视觉观察场景。

更完整的回答：

> 我们当前主线使用 soundcore Work 作为夜间声音采集入口，围绕打鼾、咳嗽、起夜、环境噪声和重点标记等事件，验证“夜间声音 -> 身体信号理解 -> 晨间行动建议”的闭环。eufy 摄像头作为可选辅助能力，只用于饮食、老人活动、生活状态等非隐私视觉场景，不用于厕所、大便等敏感场景。

## 2. 当前 Demo 能演示什么？

当前 Demo 可以演示从夜间声音采集、事件识别、用户画像、健康知识库匹配，到每日饮食、运动、恢复建议生成的完整闭环。

更完整的回答：

> 当前 Demo 可以切换五类用户画像，展示首页今日状态、睡眠页夜间声音事件、饮食页 kcal 估算、信号页排便/舌苔/口气记录、日报页个性化建议，以及架构页从 soundcore Work 原型到未来手表/手环/项链的演进。当前数据以 mock 为主，但前后端、报告生成和 adapter 结构已经跑通。

## 3. 为什么这不是普通睡眠 App？

普通睡眠 App 通常只告诉用户睡了多久、打鼾多少、睡眠分数多少。  
观息 SenseLoop 更进一步，把夜间声音和用户画像、饮食、排便、舌苔、口气等身体信号结合起来，生成第二天可执行的饮食、运动和恢复建议。

推荐回答：

> 我们不是只做“昨晚报告”，而是做“今天行动建议”。用户真正关心的不是睡眠分数本身，而是今天能不能喝咖啡、该不该运动、怎么吃、怎么恢复，以及哪些异常需要持续观察。

## 4. 为什么这不是脱离硬件的空想？

当前原型使用 Anker 官方 **soundcore Work** 作为声音采集入口，围绕真实设备、真实夜间场景和可演示 App 闭环设计。  
未来手表、手环或项链是硬件演进方向，不是当前 Demo 的唯一依赖。

推荐回答：

> 当前我们先用 soundcore Work 验证最关键的数据入口和建议闭环。即使完整健康穿戴硬件还没有做出来，soundcore Work 已经可以承担夜间声音采集和重点标记的角色，这让原型不是纯概念，而是基于官方硬件能力的阶段性验证。

## 5. 没有真实 SDK 怎么办？

推荐回答：

> 我们的工程设计里把真实硬件能力放在 adapter 层。没有 SDK 时，Demo 使用 mock adapter 和上传音频入口跑通完整闭环；拿到 SDK 后，只需要替换 soundcore adapter，不需要推翻前端页面、数据结构和报告生成逻辑。

当前状态：

- 已有前端 Demo。
- 已有 Python 后台骨架。
- 已有 mock 数据。
- 已有 soundcore / eufy / LLM adapter 占位。
- 真实 SDK 接入：当前未接入，取决于官方现场开放能力；工程上已通过 soundcore adapter 预留接入点。

## 6. 为什么需要 soundcore Work？

推荐回答：

> 因为 SenseLoop 的当前核心场景是夜间声音健康洞察。soundcore Work 具备录音、重点标记、佩戴/放置灵活等特点，适合作为“闻”的硬件入口。我们不是把它当普通录音笔，而是把它放进睡眠和健康场景里，让声音采集进入后续理解、建议和行动闭环。

## 7. eufy 在这里起什么作用？

推荐回答：

> eufy 不是当前主线必需硬件，而是“望”的可选扩展。它可以用于非隐私视觉观察，例如饮食记录、老人夜间活动、生活状态观察。我们明确不使用 eufy 自动拍摄厕所、大便等敏感场景。

当前状态：

- 当前 Demo 中 eufy 作为未来扩展和 placeholder。
- 是否现场接入真实 eufy SDK：当前不作为主线必需能力；如现场开放能力，可接入非隐私视觉事件。

## 8. 隐私怎么保证？

推荐回答：

> 我们把隐私作为产品设计的一部分，而不是最后补一个说明。夜间原始音频优先本地处理；排便、舌苔、口气等敏感信号必须用户主动触发；默认保存结构化标签，不自动保存原图、原音频或敏感画面；家庭共享只展示摘要和趋势，不展示过度私密细节。

关键原则：

- 原始音频本地优先。
- 敏感数据手动触发。
- 默认保存标签，不保存原始隐私内容。
- eufy 不用于厕所、大便等隐私拍摄。
- 用户可以删除记录。

## 9. 会不会涉及医疗诊断？

推荐回答：

> 不会。SenseLoop 的边界是日常身体趋势观察、异常提醒和生活方式建议，不做疾病诊断，不判断具体病因，也不承诺治疗效果。连续异常时，只提示用户继续观察或咨询专业医生。

可以说：

- “打鼾片段较多，建议继续观察。”
- “排便偏干，建议补水和增加膳食纤维。”
- “连续多天异常时，建议咨询专业医生。”

不能说：

- “你患有某种疾病。”
- “我们可以诊断睡眠呼吸暂停。”
- “这个建议可以替代医生。”

## 10. 24 小时现场还能做什么？

推荐回答：

> 当前我们已经有可运行的前端、后台、mock 数据和报告生成闭环。现场 24 小时不会推翻项目，而是在现有闭环上增强真实设备和真实数据。

优先做：

1. 接入 soundcore Work SDK 或真实录音文件。
2. 把真实录音/重点标记转成 `SleepAudioEvent`。
3. 把真实声音事件接入每日报告。
4. 增加音频上传和图片上传入口。
5. 如有 API Key，接入 LLM 做文案润色。
6. 如有 eufy 能力，接入非隐私视觉事件。

Fallback：

- 没有 SDK：使用 mock adapter。
- 没有 API Key：使用本地规则引擎。
- 没有网络：前端和零依赖后台本地运行。
- 设备不稳定：使用预录音频和固定演示数据。

## 11. 未来为什么可以产品化？

推荐回答：

> SenseLoop 的价值不是单个传感器，而是“每天早晨给用户行动建议”的健康闭环。当前用 soundcore Work 验证夜间声音入口，未来可以自然扩展到 Watch、Band、Pendant，加入心率、脉搏、血氧、运动、口气、图像等多模态信号，形成 Anker 在健康穿戴方向的新产品线。

产品化路径：

1. 第一阶段：soundcore Work 验证夜间声音和建议闭环。
2. 第二阶段：加入手机拍照、eufy 非隐私视觉观察和更多用户反馈。
3. 第三阶段：演进为 SenseLoop Watch / Band / Pendant，集成声音、图像、心率、脉搏、血氧、口气等传感能力。

## 13. 如果评委问“你们现在最小可交付是什么？”

推荐回答：

> 当前最小可交付是一个本地可运行的 HTML Demo + Python 后台骨架。它可以演示五类用户画像下，从夜间声音事件到每日健康建议的完整体验。即使没有 SDK、没有 API Key、没有真实音频，Demo 也能稳定运行；一旦拿到官方硬件能力，就可以通过 adapter 接入真实数据。

## 14. 如果评委问“为什么选择健康场景？”

推荐回答：

> 因为声音在健康场景里有天然价值。夜间打鼾、咳嗽、起夜、环境噪声这些信号发生频率高，但用户平时很少系统观察。soundcore Work 的录音和重点标记能力，刚好可以把这些夜间信号采集下来，再通过 App 转成第二天的行动建议。

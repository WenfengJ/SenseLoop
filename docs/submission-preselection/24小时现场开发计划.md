# 24 小时现场开发计划

## 总原则

现场不是从零做 Demo，而是在当前已经部署的 v2 原型上做真实数据接入、演示打磨和答辩准备。

当前已有基础：

- 前端已可运行。
- 后端 FastAPI 已可运行。
- PostgreSQL + pgvector 已接通。
- 游客/邮箱验证码登录已接通。
- 多健康档案已接通。
- 岐黄问诊助手 API 已接通。
- 图片/PDF 上传和本地磁盘保存已接通。
- 占位中医知识库和 RAG 检索已接通。
- 线上 Demo 已部署。

现场优先级：

```text
真实 soundcore 样例
  -> 稳定演示视频
  -> 核心页面截图
  -> 问诊问题打磨
  -> 评委问题回答
  -> 线上部署验证
```

## 第 0-2 小时：环境和线上版本确认

- 拉取最新代码。
- 确认 `.env`、DeepSeek API、本地数据库和上传目录。
- 启动前端和后端。
- 验证线上 Demo：
  - 前端地址。
  - `/health`。
  - `/api/db/status`。
  - 问诊助手。
  - 图片/PDF 上传。
  - 邮箱验证码登录。
- 固定一套演示账号和健康档案。

验收：

- 现场网络下线上版本可访问。
- 本地版本可作为备用。
- 前后端日志无明显错误。

## 第 2-5 小时：接真实 soundcore 样例

优先目标：

- 获取 soundcore Work 真实录音样例或现场导出的音频文件。
- 整理 1-2 个可解释的夜间声音案例。
- 将样例映射成 `SleepAudioEvent`：
  - 鼾声。
  - 咳嗽。
  - 夜醒。
  - 起夜。
  - 环境噪声。
- 在检测页和今日页展示真实/上传来源。

Fallback：

- SDK 不可用：使用真实录音文件 + 手动标注。
- 录音质量不稳定：使用预先准备的样例事件。
- 现场没有设备权限：明确说明 adapter 已预留，当前用 soundcore 样例验证数据结构。

## 第 5-8 小时：打磨问诊助手问题

目标不是炫技聊天，而是让评委看到 Agent 能串起产品闭环。

建议固定 3 个演示问题：

1. `结合昨晚鼾声和夜醒，今天运动强度怎么安排？`
2. `我舌苔偏干、排便偏干，和昨晚睡眠恢复有关系吗？`
3. `这份体检报告里哪些项目需要我继续观察？`

优化重点：

- 回答要引用当前档案。
- 回答要引用昨晚声音。
- 回答要引用舌苔/排便/报告摘要。
- 回答要有知识库依据。
- 回答要明确医疗边界。
- 不要说“我能诊断疾病”。

## 第 8-11 小时：录屏和核心截图

录屏顺序：

```text
今日页 -> 检测页 -> 舌诊/资料上传 -> 问诊助手 -> 报告 -> 我的/邮箱验证码登录
```

必须截图：

- 今日页：昨晚睡眠声音摘要和今日建议。
- 检测页：四诊入口。
- 夜间声音详情：鼾声、咳嗽、夜醒等事件。
- 舌诊/资料上传：图片/PDF 进入健康档案。
- 问诊助手：上方状态卡 + 回答。
- 报告页：结果沉淀和依据来源。
- 我的页：邮箱验证码登录、多档案、出生年月日/时辰、四诊档案信息。

要求：

- 截图干净，不露开发者无关信息。
- 文字尽量面向用户，不出现内部实现口吻。
- 录屏要保留 Anker / soundcore 硬件存在感。

## 第 11-14 小时：补演示材料

- 更新 3 分钟视频脚本。
- 更新 Demo 链接与运行方式。
- 更新 Roadmap。
- 更新评委 Q&A。
- 补核心截图到提交目录。
- 检查 README 是否和现场版本一致。

重点口径：

- 这是 Anker 录音笔场景延展，不是普通健康 App。
- 睡眠声音是 MVP 主线。
- 舌苔、排便、资料上传是四诊辅助。
- 中医知识库负责解释依据和边界。
- Agent 形成个人健康助手，而不是一次性报告页面。

## 第 14-17 小时：线上部署和回归验证

- 构建前端。
- 重启后端。
- 部署到服务器。
- 单独 scp `.env` 或后端环境文件，不进 git。
- 验证：
  - 首页加载。
  - 检测页跳转问诊。
  - 报告解读按钮可用。
  - 文件上传可用。
  - 问诊助手可用。
  - 登录/新建档案可用。
  - `/health` 和 `/api/db/status` 正常。

## 第 17-20 小时：准备评委问题回答

重点准备：

- 为什么是中医四诊 Agent？
- RAG 知识库从哪里来？
- 和普通健康 App 的区别？
- 隐私怎么做？
- 为什么 MVP 先用本地磁盘，不直接上对象存储？
- AI 误判怎么办？
- 是否诊断疾病？
- soundcore 没接真 SDK 怎么解释？
- 为什么 Anker 做这个有价值？
- 后续商业化怎么走？

要求：

- 每个问题回答 30 秒以内。
- 先讲产品价值，再讲技术实现。
- 不回避当前 mock / 样例数据的边界。
- 明确说“当前不做医疗诊断”。

## 第 20-24 小时：最终彩排

- 跑一遍 3 分钟 Demo。
- 跑一遍无网络本地备用方案。
- 准备备用视频。
- 准备截图 PDF。
- 准备提交链接。
- 检查二维码和线上地址。
- 检查 GitHub 仓库是否干净。

## 风险预案

| 风险 | 预案 |
| --- | --- |
| soundcore SDK 不可用 | 用真实样例录音或手动标注事件 |
| AI API 不稳定 | 使用已生成示例回答和本地规则兜底 |
| 网络不稳定 | 本地前后端演示 |
| 服务器不可访问 | 本地录屏和截图兜底 |
| 文件上传失败 | 使用预置资料摘要演示 |
| 问诊回答太发散 | 固定 3 个演示问题 |
| 时间不够 | 优先保证今日页、检测页、问诊助手、报告页闭环 |

## 现场完成标准

现场结束前必须保证：

- 有一个稳定 3 分钟录屏。
- 有一套核心截图。
- 有线上 Demo 或本地备用 Demo。
- 有评委 Q&A 口径。
- 有 soundcore 数据接入解释。
- 有清楚的隐私和医疗边界说明。
